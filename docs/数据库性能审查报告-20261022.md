# 统一分析平台数据库性能审查报告

日期：2026-10-22
审查对象：`data/lottery_tools.sqlite3`（jiuxiang 243272 行 / dawei_shahao 125378 / pingte 74248，合计 442898 行）
审查方式：EXPLAIN 分析、临时库副本压测、只读接口实测

## 一、结论

表结构和索引本身没有问题。真正的瓶颈是两处应用层实现：

1. 快照接口每次全量读整项目并逐条算 sha256。
2. 每日统计的连对筛选对每个站名重算一次整段历史（N×M 次）。

## 二、已完成的处置

### 1. 数据安全（最高优先级）

- **完整备份**：`data/backups/lottery_tools-20261021-163913-380.sqlite3`
  - 走项目自带 `createBackup()`（`node:sqlite` backup API），一致性快照。
  - 校验：`integrity_check = ok`，442898 行，与主库逐模式行数完全一致。
- **WAL checkpoint**：33.6 MB 未 checkpoint 的 WAL 归零，那 934 条历史数据已落盘到主库。
  - 验证：主库单独打开（不带 WAL）可查到完整 442898 行。

> 此前的风险：那 934 条历史数据只在 WAL 里，只备份 `.sqlite3` 主文件会丢数据。

## 三、未做的部分及原因

1. **`getSnapshotDataVersion` 的 `max(updated_at)` 扫描（31 ms）**
   - 需新增 `(project_id, updated_at)` 索引，库会从 72.6 MB 涨到约 89 MB。
   - 当前 31 ms 可接受，性价比不足，未做。

2. **快照按 mode 过滤**
   - 评估后发现：日统计页、长期榜、缺失目录页都需要项目内全部模式的数据。
   - 只传当前 mode 会破坏这些页面，收益 5 倍但风险高，未做。

3. **并发阻塞**
   - `node:sqlite` 是同步 API 单连接，跑长期榜（2.08 s）期间其他请求被阻塞。
   - 根治需要改造成 worker 线程或多连接，属架构改动，未做。
   - 当前已把 health 降到 1 ms，日常影响可接受。

## 四、建议的后续动作

1. 定期对库做 `PRAGMA wal_checkpoint(TRUNCATE)`，避免 WAL 再次堆积。
2. `data/backups/` 已累积 365 MB / 15 个文件，建议只保留最近 3–5 份。
3. 若长期榜并发阻塞成为实际问题，再考虑 worker 线程方案。
