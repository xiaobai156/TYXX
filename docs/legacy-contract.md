# 旧版行为契约

> 审计基线：2026-07-27。本文档是统一平台重构的旧版行为基准。旧项目只读，不以旧版 Supabase 实现细节作为新架构要求，但所有明确的业务结果、输入兼容和操作范围必须由自动化测试锁定。

## 1. 范围与术语

三个源项目及目标项目代码：

| project_id | 源项目 | 模式数 |
| --- | --- | ---: |
| `pingte` | 平特云端 | 3 |
| `dawei_shahao` | 大围+杀号云端 | 4 |
| `jiuxiang` | 段-合-行-肖-半波-半头-尾云端 | 10 |

注意：旧页面叫“九项综合”，但当前实际有 10 个模式，因为 `shayixiao2`（杀肖第二版）是独立模式。统一平台必须保留 17 个模式，不能因旧名称而合并或遗漏。

术语：

- **项目日**：`project_id + date`，日期必须是有效且规范的 `YYYY-MM-DD`。
- **模式日**：`project_id + date + mode_id`，含一个 `query` 和零到多个目录条目。
- **目录条目**：`project_id + date + mode_id + name` 唯一，业务字段至少含 `content`，源数据有值时保留 `original`。
- **生日**：某项目、某模式、某目录第一次出现的日期。
- **全局缺失日**：九项旧版中的 `isMissingDay=true`，表示该日期是日期轴上的缺口，不等同于某个目录在正常日期未上传。
- **派生统计**：可从查询值和目录条目重建的数据，不是迁移真源。

## 2. 全局不变量

以下规则必须在 API、数据库和前端三层同时成立：

1. 所有读取、缓存键、唯一键、写入、删除、改名、统计和导出都必须包含 `project_id`。同名模式、日期或目录不得跨项目串联。
2. 单模式保存是“替换该模式日”：在一个事务中更新 query、删除该模式日旧目录并插入本次目录；不得影响同项目同日的其他模式。
3. “清空本日”是“删除整个项目日”：删除该项目该日全部模式的 query 和目录；不得影响其他项目的同一天。
4. 批量分发是“同一项目、同一模式、同一目录名跨最多 20 天 upsert”，每行必须同时有日期、query、content。整个提交必须是一个事务。
5. 目录全局改名只作用于同一项目和模式的全部历史；目标名在该项目和模式任何日期已存在时拒绝。
6. 单日删除目录只删除一个 `project_id + date + mode_id + name`；全历史删除只删除一个 `project_id + mode_id + name`。
7. query 不能参与目录数、生日、连对连错、排行榜、日历完整度、断更目录或目录管理。
8. 新库以独立 query 字段存结果，不把系统 query 伪装成业务目录。迁移时识别源系统记录，但不得静默丢弃无法归属的冲突内容。
9. 任一持久化操作失败时，数据库保持操作前状态；前端只在事务成功后更新内存状态。
10. 修改某模式某日期后，该模式从最早受影响日期起的分析、走势、每日统计和一次过滤缓存全部失效。新增项目日时，九项旧行为要求 10 个模式都失效。
11. 统计缓存必须带规则版本；版本不匹配时丢弃缓存并从真源重算。
12. 过去日期默认锁定。保存过去日期必须显式启用“允许自主修改历史”；本地单库不再需要旧版的云端/缓存指纹比较。

### 2.1 系统 query 名迁移

源项目的表示不同：

| 项目 | 源表示 | 识别规则 |
| --- | --- | --- |
| 平特 | `daily_queries` 主要保存日期，query 常在 `data_entries.__QUERY__` | `QUERY`、`_QUERY_`、`__QUERY__` 等大小写变体均按系统名 |
| 大围 | `daily_queries` 有 `dawei_query`、`shahao_query`、`shengxiao_query`；`shaxiao` 共用 `shahao_query` | 旧派生统计只排除 trim 后大小写无关的裸 `QUERY` |
| 九项 | `daily_queries` 主要保存日期，每模式 query 使用 `data_entries.__QUERY__` | 精确 trim 后的 `__QUERY__` |

目标规则统一为：匹配 `^_*QUERY_*$`（大小写无关）的名称均不得成为业务目录。迁移器先把可确定的内容写入模式日 query，再把源记录写入迁移审计清单；同一模式日出现多个不同 query 时必须报告冲突，不能任选一个覆盖。

## 3. 17 个模式的命中契约

### 3.1 平特项目

| mode_id | 名称 | content | query | `correct=true` |
| --- | --- | --- | --- | --- |
| `pingteyixiao` | 平特一肖 | 一个或多个生肖 | 当期全部生肖，可多个 | content 与 query 至少一个生肖重合 |
| `pingtewei` | 平特尾 | 一个或多个 `0尾` 至 `9尾` | 当期全部尾数，可多个 | content 与 query 至少一个尾数重合 |
| `shaliangxiao` | 杀两肖 | 恰好两个不同生肖 | 一个特码生肖，或一个 `01-49` 特码号 | 特码生肖不在被杀的两个生肖中 |

解析和显示要求：

- 生肖只识别 `鼠牛虎兔龙蛇马羊猴鸡狗猪`，去重并保留首次出现顺序。
- 尾数中的数字逐位解释，例如 `24尾` 归一为 `2尾4尾`。
- 杀两肖 content 的第一字段必须是两个不同生肖，例如 `马蛇 资料名`。
- 杀两肖列表中的“高亮命中”表示实际生肖被杀中，因此它与业务 `correct` 相反；统计只能使用 `correct`。
- 特码号到生肖使用下文的静态生肖号码表。

### 3.2 大围+杀号项目

| mode_id | 名称 | content | query | `correct=true` |
| --- | --- | --- | --- | --- |
| `dawei` | 大围 | 号码集合 | 第一个开奖号 | query 在 content 中 |
| `shahao` | 杀号 | 号码集合 | 第一个开奖号 | query 不在 content 中 |
| `shengxiao` | 生肖 | 生肖集合 | 第一个开奖生肖 | 见日期切换规则 |
| `shaxiao` | 杀五码 | 号码集合 | 与 `shahao` 共用开奖号 | query 不在 content 中 |

特殊规则：

- `shengxiao` 在 `2026-05-21` 之前是“包含开奖号算对”；从 `2026-05-21`（含）起改为杀号逻辑，即“不包含开奖号算对”。这个日期边界不能丢失。
- 繁体 `龍/雞/馬/豬` 归一为 `龙/鸡/马/猪`。
- `shahao` 与 `shaxiao` 共享同一 query。保存任一模式的 query 后，同日另一模式读取到的 query 必须同步变化；目录条目仍互相独立。
- 批量/上传校验：大围恰好 36 个数字；杀号 1 至 30 个数字；杀五码默认恰好 5 个数字，目录名精确为 `拔树寻根` 时恰好 6 个；生肖只能为汉字。
- 旧工作台手工保存只强制杀五码的 5/6 数量，并未强制大围 36 或杀号 1-30。为兼容旧输入，不能在没有迁移报告的情况下把批量限制直接套到历史数据读取。

| `shabanbo` | 杀半波 | `红单/红双/蓝单/蓝双/绿单/绿双` |

## 4. 录入与解析契约

### 4.1 通用清洗

- 去除零宽字符和 BOM，把全角空格转普通空格。
- `。 ， ． ； ： 、 .` 在旧解析器中通常归一为逗号。
- 空行、单独 `-`、单独一位或两位数字行属于瘦身/摘要行，工作台解析时跳过。
- 同一模式日目录名重复时，工作台拒绝整次保存。
- `name` 缺失时旧工作台使用 `未命名`；新实现应保持可读取，但保存前仍做同名冲突检查。

项目解析器：

- 平特：内容在前、目录名在后。平特一肖先取开头生肖串；平特尾先取开头数字/尾串；杀两肖先取开头两个生肖。
- 大围：数字模式优先提取连续数字序列并把剩余文本作为目录名；杀号允许“单个前导号码 + 目录名”；生肖模式第一字段是内容，其余为目录名。
- 九项：第一空白字段是类型 content，其余文本是目录名。一次过滤另有更宽松的类型前缀解析，仍必须归一到合法类型。

保存前要求 query 和至少一条有效原始资料。九项还必须拒绝系统名和不属于当前模式的 content；平特杀两肖必须拒绝非两个不同生肖；大围杀五码执行 5/6 数量规则。

### 4.2 上传工具兼容

统一平台若接管旧上传工作流，必须兼容以下文件约定：

- 平特：同批必须有 `*平特肖.txt`、`*平特尾.txt` 和唯一的 `N期-二肖.txt`。平特一肖 query 是 7 个开奖号对应生肖去重串，平特尾 query 是 7 个开奖号尾数去重串，杀两肖 query 是特码号。
- 大围：同批必须有同一月日的 `M.D大围.txt`、`M.D生肖.txt`、`M.D杀数字.txt`、`M.D杀五码.txt`；年份取运行时当前年。四模式作为一个完整项目日提交。
- 九项：同一期必须有 `N期-半头/头/一波/半波/合/肖/肖-新增/段/五行/尾.txt`；10 模式作为一个完整项目日提交。
- 大围和九项上传器拒绝重复目录名。平特上传器会把重复名自动改为 `名称 #2`、`名称 #3`；迁移现有记录时必须保留这些已生成名称。
- TXT 支持 `utf-8-sig`、`utf-8`、`gb18030`。

## 5. 页面与操作流程

统一入口应保留以下业务路径，并以项目切换器限定上下文：

1. 日历：选择月份，点击日期进入工作台；数据、状态和缓存均按当前项目显示。
2. 工作台：在当前项目的模式间切换；粘贴资料、输入 query、按目录名搜索；实时分为正确区和错误区并按当前连对/连错展示。
3. 保存：校验后原子替换当前模式日。过去日期需要显式解锁。
4. 清空本日：二次确认后原子删除当前项目日全部模式。
5. 详细分析：切换模式，查看目录状态、当前持续天数、总错次、最高连对、最高连错、命中率、近 7/10 天、近 30 错次、入库天数；大围和九项另有最低连对。
6. 趋势：从目录行打开走势图；正常缺目录按项目规则显示错，全局缺失日显示缺数据。
7. 每日统计：按月倒序展示所有模式，支持每模式“只保留此前已连对 >= N 天”的对比筛选。
8. 一次过滤：只读取历史，不写业务数据库；默认剔除上一参考期错误目录，再可选剔除截至目标日连对不足 N 天的目录；用户可在卡片上继续手动剔除；三个输出复制时必须保持原始行文本和顺序。
9. 批量分发：一个模式、一个目录名、最多 20 个日期；每行包含 content/date/query；确认后一次事务提交。
10. 目录管理：全历史改名、删除单日、删除全历史；断更 >= 2 天的目录可从断更面板删除。

项目切换时至少隔离：当前日期、当前模式、搜索词、分析模式、一次过滤输入与手动选择、每日统计筛选、复制范围、派生缓存和批量草稿。

## 6. 历史与统计契约

### 6.1 共同定义

- 日期升序处理，从目录生日开始。
- `correct=true` 连续形成连对，`false` 连续形成连错；状态变化时持续数重置为 1。
- `daysInSystem` 只计算实际产生 true/false 的日期。
- `totalBroken` 是 false 的总数。
- 近 7、近 10 和近 30 均以该项目规则产生的有效状态序列为准。
- 命中率分母不得包含没有可判定结果的 `null`。
- 断更天数按目录最后一次实际出现日期到自然今天的 UTC 日差计算。

### 6.2 缺资料和缺日差异（不得统一）

| 项目/页面 | 正常项目日中，生日后的目录未上传 | 没有有效 query | 全局缺失日 |
| --- | --- | --- | --- |
| 平特详细分析 | 算错 | 不计 | 无专用状态 |
| 平特每日统计 | 算错，并纳入 total | 不计 | 无专用状态 |
| 大围详细分析 | 算错 | 不计 | 无专用状态 |
| 大围每日统计 | 只统计当天实际上传目录，未上传不入 total | 不计 | 无专用状态 |
| 九项详细分析 | 算错；模式日不存在或 query 非法也算错 | 算错 | 追加 `null`，重置当前连串，不增加 daysInSystem |
| 九项每日统计 | 只统计当天该模式实际上传目录 | 不计 | 整日 total=0 |

九项 `null` 仍保留在走势图/状态历史中用于显示缺口，但推荐评分先过滤 `null` 再取最近 30 个 true/false。

### 6.3 推荐评分差异

三个项目共享 30 期、6 个 5 期分段和风险惩罚的大部分公式，但有一个会改变排序的差异：

- 大围的 `recent7Switches` 是最近 7 个状态相邻变化的次数。
- 平特和九项的同名字段实际是最近 7 期“错误段开始次数”（连续多个 false 只算一个错误段）。

不能直接共用一个未参数化的评分函数。目标实现必须把此行为作为项目策略，并用固定序列测试，例如 `[true,false,false,true,false]`：大围切换数为 3，平特/九项错误段数为 2。

其他现行评分要点：最近 30 期按 5 期分 6 段，权重为 `0.29/0.25/0.20/0.14/0.09/0.03`；覆盖率低于 0.40、最近 7 命中率低于 0.43 等会触发强惩罚。重构不应在迁移过程中顺便调整权重。

### 6.4 每日统计附加结果

- 平特杀两肖：统计每个被杀生肖出现次数，显示开奖号生肖及出现次数，并显示频次第一、第二档是否包含开奖号；同频多个生肖均属于该档。
- 大围生肖：显示出现频次前两档及开奖生肖是否在档内。
- 大围杀号/杀五码：对 `01-49` 频次做稠密排名，开奖号位于前三档即显示命中。
- 九项：按合法类型统计最高频次；显示第一名是否包含 query 类型、第一名次数，以及 query 类型被内容命中的目录数。
- 连对筛选只根据目标日期之前的历史状态判断，不能把目标日结果泄漏进筛选条件。

## 7. 一次过滤项目差异

共同规则：参考日期必须早于目标日期；先按参考期错名剔除，再应用可选连对阈值，最后应用手动剔除；输入不入业务库。

| 项目 | 参考日期 | 自动数据源/联动 |
| --- | --- | --- |
| 平特 | 目标日前最后一个该模式 query 有效且有 parsed 的日期 | 仅手工粘贴和剪贴板 |
| 大围 | 目标日前最后一个该模式 query 非空且有 parsed 的日期 | `38800` 固定目录服务；复制大围保留名单同步分档；分析复制名单同步高手榜 |
| 九项 | 目标日前最后一个项目日期，不要求该模式 query 有效 | `38799` 固定目录服务或浏览器目录句柄；保留名单同步九项汇总；分析名单同步专家排行 |

九项固定目录后缀：`半头/头/一波/半波/合/肖/二肖/段/五行/尾`。大围固定目录后缀：`大围/杀数字/生肖/杀五码`。

这些本地桥接是现有工作流，不可在合并 HTML 时静默删除。统一服务可以把 `38799/38800` 合并到同一个端口，但必须保留等价 API 或同时迁移所有消费者。

## 8. 数据迁移契约

每个源库独立导出，目标导入流程：

1. 冻结导出时间并保存原始 JSON/CSV，只读保留。
2. 规范化项目、日期、模式、query、目录名和 content；不得在此步骤重算业务结果。
3. 对每个源主键建立迁移清单：`source_project/source_table/source_key -> target_key/status`。
4. 同一目标键内容完全一致时去重；内容不一致时输出冲突并停止该项目导入。
5. query 系统条目按 2.1 转入模式日 query；原始条目保留在迁移审计文件，不进入业务目录。
6. 导入使用单事务；失败回滚整个项目批次。
7. 只迁移真源和必要元数据；`directory_stats`、`directory_daily_stats`、游标和浏览器缓存全部从目标真源重建。
8. 校验每项目、日期、模式的 query 数、目录数、最早/最晚日期和内容哈希；要求零缺失、零多余、零未处理冲突。
9. 对抽样日期运行本文命中、缺资料、统计和一次过滤契约，与旧版输出比对。
10. 完成备份恢复演练后才允许切换为本地唯一写入源；旧云端先只读观察，不立即删除。

## 10. 可复用与不可直接合并

哈希审计结果：三项目完全相同的现成模块只有 `echarts.min.js`、旧 `supabase.min.js`、`v2-shell.js` 和 `00-ui-dialog.js`。Supabase 模块在本地版应删除，因此真正可直接复用的是壳层、对话框和 ECharts。

适合提取为共享核心，但必须注入项目策略：

- 页面路由、项目/模式切换、日历框架、通用对话框。
- SQLite API 客户端、事务错误处理、备份/恢复。
- 索引构建、缓存失效、统计遍历框架。
- 分析表、趋势图、复制范围、断更面板、一次过滤框架。
- 通用清洗、日期处理和 HTML 转义。

不可直接共用一个硬编码实现：

- 17 模式解析、query 合法性和命中函数。
- 三项目缺行/缺日统计口径。
- 平特/九项与大围的 `recent7Switches` 计算。
- 大围共享杀号 query、生肖日期边界和杀五码例外。
- 每日统计的附加排名。
- 三项目一次过滤参考日期与外部联动。
- 上传文件发现规则和完整批次规则。

## 11. 已确认旧版缺陷（不作为必须复制的行为）

1. 九项日历完整度函数仍引用不存在的 `dawei/shahao`，五月会错误显示不完整。
2. 三项目首页“最高连对/最长连错”目前都被代码固定显示为 `-`，不是有效统计。
3. 九项的名称叫九项但实际 10 模式；界面文案容易造成漏迁。
4. 平特和九项批量页没有像大围一样显式拒绝重复日期。
5. 大围和九项批量确认文案仍称“串行”，实际 RPC 是单事务；九项输入提示还残留杀五码文案。
6. 九项“打开汇总统计”使用绝对 `file:///C:/...` 地址，不可移植。
7. 生肖号码表静态绑定当前号码年份，长期使用必然跨年失效。目标必须按开奖日期保存规则版本；在新规则确认前先保持当前映射并发出明显的规则到期检查。
8. 大围文件名不含年份，上传器直接使用运行时当前年，跨年补历史可能写错年份。
9. query 系统名识别规则在三个项目不一致，统一迁移必须扩大识别并生成冲突报告。

## 12. 建议迁移顺序

1. 先完成统一 SQLite/API、项目隔离、事务、备份和 query 独立存储，并为本文验收场景建立测试夹具。
2. 先迁大围项目：现有本地数据最大，原子保存、恢复、并发缓存和统计测试最完整，可最早暴露单库与事务问题。
3. 再迁平特项目：模式少，但可验证多值 query、杀两肖反向正确性和“缺目录计错”的另一套每日统计口径。
4. 最后迁九项：10 模式、全局缺失日、静态分类映射、两个本地桥接和独立每日统计口径，复杂度最高。
5. 每完成一个项目，先做旧/新双读结果比对，再开放新平台写入；不得等 17 模式全部完成后一次性总验收。
